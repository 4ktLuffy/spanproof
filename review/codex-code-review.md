# SpanProof correctness review

Reviewed all eight oracles, conventions, detectors, CI gating, capture, matrix parsing, and fixture truth semantics. Findings below are ranked by severity. Paths are relative to this directory. No package files were changed.

Validation: the existing suite passed **34 tests** using the requested interpreter, with bytecode and pytest cache writes disabled. Small in-memory Python reproductions confirmed the behaviors below; external provider calls and environment installation were not required. Passing tests do not cover these cases.

For concise reproductions, snippets using `span`, `result`, `GOOD`, and `T` refer to the helpers in `spanproof/tests/test_oracles.py`; snippets using `AG`, `tool`, `chat`, and `kinds` refer to `spanproof/tests/test_detectors.py`. From `spanproof/`, they can be imported after `sys.path.insert(0, 'tests')`. All snippets assume the corresponding package modules are imported.

## High severity

### 1. CI reports success when nothing could be checked

**Location:** `spanproof/spanproof/gate.py:30–34`, `:60`, `:78`.

**Trigger:** pass either of these run documents to `gate.main`:

```json
{"results": [{"scenario": "s", "crashed": true, "stderr": "worker failed"}]}
```

```json
{"cells": [{"env": "openai-base", "install_error": "installation failed", "results": []}]}
```

**Observed:** both print `0 new, 0 fixed, 0 known` and return **0** without a baseline. An empty run behaves the same. With a baseline, missing findings are reported as fixed even if their scenarios crashed or were not run.

**Why wrong:** `findings()` ignores execution health and coverage. A broken provider version or worker can therefore turn a previously failing check into a green CI run. Absence of evidence is also incorrectly offered as evidence of a fix.

**Suggested fix:** validate run/cell execution status before comparing findings; fail on crashes, installation failures, or unexpectedly empty coverage. Track completed scenario/mode/cell coverage and only classify baseline findings as fixed when their checks actually ran successfully. Handle intentionally unsupported scenarios explicitly.

### 2. Baseline signatures merge distinct defects and version regressions

**Location:** `spanproof/spanproof/gate.py:23–25`, `:30–34`.

**Trigger:** two findings for scenario `s`, mode `default`, check `structure`, attribute `parent_span_id`, severity `high`: one says a span's parent was never sent; the other says an LLM span is outside the agent. These are separate rules generated by `check_structure`, but `signature()` returns the same string. A baseline containing the first suppresses the second. Similarly, the same finding newly appearing in a previously healthy matrix version is suppressed if another version already had it.

**Observed:** the two structural findings have equal signatures and `findings()` collapses them into one dictionary entry.

**Why wrong:** the key identifies a broad attribute/check category, rather than a defect. Distinct failures, calls, and matrix cells overwrite each other, hiding new regressions.

**Suggested fix:** add stable rule identifiers to findings and include them in the signature, along with relevant call/scope identity. Preserve matrix cell identity through flattening and baseline comparison. Use stable requested-version labels such as `latest` where appropriate, rather than volatile wording or numeric observations.

### 3. Reporting spurious tokens when truth is zero crashes all checks

**Location:** `spanproof/spanproof/oracles.py:186–189`.

**Trigger:** a completed call with `Truth(1, 1)` and a span reporting `gen_ai.usage.cache_read.input_tokens = 1`.

```python
oracles.check_aggregation(result(
    [span(**{'gen_ai.usage.cache_read.input_tokens': 1})],
    calls=[{'truth': Truth(1, 1).as_dict(), 'completes': True}],
))
```

**Observed:** `ZeroDivisionError: division by zero`.

**Why wrong:** zero cache/reasoning/output usage is normal. The erroneous positive SDK value is precisely what this oracle should flag, but formatting `naive / billed` aborts `run_all`. The runner does not catch this exception, so it can prevent the run or matrix report from being written.

**Suggested fix:** report the mismatch without a ratio when billed usage is zero. Add zero-ground-truth cases for each aggregated meaning.

### 4. Malformed child usage crashes rollup before type findings can be returned

**Location:** `spanproof/spanproof/oracles.py:224`.

**Trigger:** an agent reports numeric input usage `1200`; its child LLM reports the string `"1200"` for `gen_ai.usage.input_tokens`.

```python
a = span(op='gen_ai.invoke_agent', sid='a',
         **{'gen_ai.usage.input_tokens': 1200})
c = span(parent='a', **dict(GOOD,
         **{'gen_ai.usage.input_tokens': '1200'}))
oracles.run_all(result([a, c]))
```

**Observed:** `TypeError: unsupported operand type(s) for +: 'int' and 'str'`.

**Why wrong:** detecting invalid emitted data is the purpose of the tool. Aggregation runs before conventions and sums unchecked values, discarding both earlier findings and the eventual type finding.

**Suggested fix:** validate numeric child values before arithmetic, reject booleans, and distinguish invalid/missing usage from zero. Return an invalid-data finding and skip an indeterminate rollup rather than raising or reporting a fabricated sum.

### 5. Greedy fallback consumes another call's exact response-ID match

**Location:** `spanproof/spanproof/oracles.py:41–55`.

**Trigger:** calls have response IDs `A` then `B`. Span start order is: span `b` carries ID `B`; span `a` has no response ID. These can be overlapping calls with different start ordering between the provider script and instrumentation.

**Observed:** `match_calls()` returns `[(0, b), (1, a)]`, although `B` has an exact match and `A` can use the anonymous span. The first call's fallback steals `b` before the second call is considered.

**Why wrong:** usage and identity checks compare different calls. Different token counts/models produce false mismatches and can conceal a real per-call error. Fallback also accepts a span with an explicitly conflicting ID.

**Suggested fix:** reserve all exact response-ID matches in a first pass, then match remaining calls to compatible anonymous spans in a second pass. Respect operation where available, and leave unmatched calls unmatched instead of overriding conflicting identity evidence.

### 6. Cyclic parent relationships hang the structural and rollup checks

**Location:** `spanproof/spanproof/oracles.py:129–134`, `:206–212`.

**Trigger:** agent span `a` has `parent_span_id = 'a'`, numeric input usage, and a client child whose parent is `a`; set `result.agent = {'tools': []}`.

**Observed:** `check_structure()` never returns from `ancestors()`. Calling `check_rollup()` separately also never finishes traversing the self-child. Both were reproduced with a 50 ms signal deadline, which interrupted the otherwise unbounded traversal.

**Why wrong:** the invalid relationship is not reported as a structural finding. The review process instead loops indefinitely and can exhaust memory. The worker subprocess timeout does not cover these parent-process oracle calls.

**Suggested fix:** track visited IDs during ancestor/descendant traversal and explicitly report self-parenting/cycles. Validate uniqueness of span identities as well. Apply bounded traversal to the analogous walks in `detectors.py`.

## Medium severity

### 7. Type checking stops after the first span with the same operation and key

**Location:** `spanproof/spanproof/oracles.py:242–255`.

**Trigger:** two `gen_ai.chat` spans: the first has `gen_ai.response.model = 'm'`; the second has `gen_ai.response.model = 123`.

```python
oracles.check_conventions(result([
    span(**{'gen_ai.response.model': 'm'}),
    span(sid='s2', **{'gen_ai.response.model': 123}),
]))
```

**Observed:** `[]`.

**Why wrong:** deduplication occurs before value validation, so one valid value suppresses all later invalid values for that operation. This can also hide invalid token types when ordinary Python numeric equality lets them pass the usage check.

**Suggested fix:** deduplicate key-level registration/deprecation findings separately. Validate every value, and deduplicate actual violations only after detecting them.

### 8. Identity checks accept wrong finish reasons and response IDs

**Location:** `spanproof/spanproof/oracles.py:307–313`.

**Trigger:** use the existing `GOOD` span and `T` truth, but change the emitted finish reason to `'["length"]'` and response ID to `'wrong'`. Truth still says `stop` and `r1`.

**Observed:** `check_identity()` returns `[]`. An empty finish-reason value also satisfies the existence check.

**Why wrong:** these attributes are checked only for key presence, although they carry identity and termination information. A truncated/tool-stopped response incorrectly labeled `stop`, or a wrong provider ID, remains undetected. A null response model similarly bypasses both model branches.

**Suggested fix:** normalize scalar/list/serialized finish-reason forms and compare their values against truth. Validate response-ID equality and treat null/empty required identity values as missing.

### 9. Successful structured tool results are mistaken for errors depending on key order

**Location:** `spanproof/spanproof/detectors.py:23–24`, `:281–282`.

**Trigger:** successful tool span, status `ok`, output `{"error":null,"ok":true}`, followed by a successful chat with text `done`.

```python
kinds([AG, tool('t', 1, out='{"error":null,"ok":true}'), chat('c', 2)])
```

**Observed:** `{'silent_tool_error'}`. Putting `ok` first avoids this particular regex match.

**Why wrong:** `_structured_error()` correctly returns false, but the independent text regex matches any object beginning with an `error` key, regardless of its value. Explicitly successful JSON becomes a false incident based on serialization order.

**Suggested fix:** parse recognized structured results first and honor their error/success semantics. Use textual heuristics only for unstructured content, rather than applying them to serialized object syntax after successful parsing.

### 10. Missing answer content is treated as proof that a failure was not acknowledged

**Location:** `spanproof/spanproof/detectors.py:285–289`.

**Trigger:** tool output `TimeoutError: failed`, followed by a completed `stop` chat with no output-content attributes. The actual answer may have explained the failure, but that integration did not record it.

**Observed:** `silent_tool_error` is emitted because `_texts(None)` is `''`, which cannot match `ACKNOWLEDGED`.

**Why wrong:** the detector claims the agent answered as if the tool succeeded without observing the answer. The function's existing acknowledgement rule cannot be evaluated when content is absent.

**Suggested fix:** distinguish unavailable content from observed empty/non-acknowledging content. Only assert a silent failure when there is adequate observed evidence; otherwise return an explicitly uncertain/unsupported result if the API needs to expose that state.

### 11. Valid JSON answers and one-token answers are reported as empty

**Location:** `spanproof/spanproof/detectors.py:92–104`, `:306–313`.

**Trigger A:** a successful final chat has `gen_ai.response.text = '42'`. `_texts()` parses it as an integer, then returns `''`. The same problem affects `true` and a structured answer such as `{"answer":42}` with no `content`, `text`, or `parts` keys.

**Trigger B:** a successful chat has no recorded output text and `gen_ai.usage.output_tokens = 1`; the real answer is the valid one-token response `Yes`.

**Observed:** both cases emit `empty_answer`.

**Why wrong:** valid application content is confused with a serialized message wrapper, and a nonzero token count is incorrectly treated as proof of emptiness. This produces false failures for short answers and structured-output applications.

**Suggested fix:** preserve nonempty raw text unless it is positively recognized as a message wrapper; do not erase JSON scalar/object answers. Treat missing content as unknown and never infer emptiness solely from a count of one token.

### 12. Cost-spike detection ignores supported usage aliases

**Location:** `spanproof/spanproof/detectors.py:323–326`; compare `spanproof/spanproof/conventions.py:21–23`.

**Trigger:** six traces for the same agent, each with one client span. Five use 100 input tokens and the sixth uses 10,000. Emit these through `gen_ai.usage.prompt_tokens` instead of `gen_ai.usage.input_tokens` (and use the accepted completion alias if output usage is present).

**Observed:** alias-only traces yield no spikes. Replacing the input key with the canonical key identifies trace index `5` as a spike.

**Why wrong:** the package explicitly accepts these aliases, but `run_tokens()` computes zero usage for them. A provider/integration using legacy conventions silently disables the cost detector or biases comparisons between mixed versions.

**Suggested fix:** normalize usage through `conventions.read_usage()` in the detector and consistently validate numeric values before summing.

### 13. Byte-backed envelope payloads silently disappear

**Location:** `spanproof/spanproof/capture.py:19–20`, `:60–61`, `:93–96`.

**Trigger:** construct a legitimate SDK envelope item using `PayloadRef(bytes=json.dumps(transaction).encode())`, where `transaction` contains a trace context and a finished transaction timestamp. Pass it through `MemoryTransport.capture_envelope()` and `flatten()`.

**Observed:** `{'spans': [], 'errors': [], 'transactions': 0}`. The equivalent JSON-backed payload is parsed. Byte-backed span and event items are also skipped by the dictionary guards.

**Why wrong:** the transport explicitly retains byte payloads but the decoder never deserializes them. A serialized-envelope path therefore creates false missing-span/error findings and loses the data needed for other checks. The inspected SDK normally emits JSON-backed items directly; this issue is conditional on using its supported byte-backed representation.

**Suggested fix:** decode JSON payload bytes for recognized event/transaction/span item types before dispatching, and report malformed payloads explicitly rather than silently treating them as absent.

### 14. Valid commented tox pins are dropped without an error

**Location:** `spanproof/spanproof/matrix.py:51–55`.

**Trigger:** this tox input:

```ini
[tox]
envlist =
    {py3.12}-openai-base-v1.0.1
[testenv]
deps =
    openai-base-v1.0.1: openai==1.0.1 # pinned
```

**Observed:** `tox_cells()` produces the `1.0.1` cell with `pins = []`. The same pin without its trailing comment is retained.

**Why wrong:** the whole-line single-nonwhitespace-token regex rejects a commented requirement. `build_env()` can then install no provider, reuse an unrelated installed provider, or resolve a provider through other dependencies, while the cell remains labeled `1.0.1`. This can hide version-specific regressions. Shared factor selectors and requirement lines containing spaces are likewise outside the parser's accepted subset.

**Suggested fix:** parse tox dependency/factor syntax and comments before extracting requirements, ideally using tox's resolved configuration. At minimum, fail loudly when a versioned cell has no provider requirement and verify the installed version matches its declared pin.

## Reviewed semantics and limits

The requested fixture accounting rules are implemented correctly in the inspected builders: Anthropic default input truth is `40 + 2048 + 512 = 2600`, and Gemini default output truth is `200 + 150 = 350`, with total `1250`. OpenAI chat/Responses counts are treated as already inclusive of cached/reasoning subsets. These behaviors were not flagged as defects.

The review exercised focused synthetic inputs and the existing unit suite, not a fresh full provider-version matrix. The capture finding is explicitly representation-dependent; the matrix finding is based on a concrete parser input rather than a claim that the current external tox checkout contains that commented pin.
